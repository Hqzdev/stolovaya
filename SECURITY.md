# Безопасность

## Сообщить о проблеме

Используйте [приватное сообщение об уязвимости на GitHub](https://github.com/Hqzdev/stolovaya/security/advisories/new). Не публикуйте секреты, cookie и действующие учётные данные в issues. Если приватная форма недоступна, создайте issue с просьбой предоставить закрытый канал без описания способа эксплуатации.

## Модель доступа

- Две учётные записи задаются в серверном окружении; регистрации и управления пользователями нет.
- Пароли сравниваются через `scrypt` и сравнение буферов за постоянное время. В PostgreSQL пароли не сохраняются.
- Случайный токен сессии хранится в HttpOnly-cookie; в базе хранится только SHA-256 токена и HMAC-версия учётных данных. Сессия действует 8 часов.
- Изменяющие запросы требуют разрешённый `Origin` и CSRF-токен. Роль проверяется серверным guard.
- Вход ограничен 10 запросами в минуту, API — 300 запросами в минуту на адрес процесса-прокси.
- Запросы SQL параметризованы, переход статуса блокирует строку в транзакции.

## Настройка

Держите `.env` вне Git и ограничьте права файла (`chmod 600 .env`). Задайте разные логины, длинные уникальные пароли, случайный `SESSION_SECRET` и собственный пароль PostgreSQL. После смены аккаунта пересоздайте контейнер API: `docker compose up -d --force-recreate api`.

Локальный Compose публикует web и PostgreSQL только на `127.0.0.1`; API доступен внутри Docker-сети. При размещении за HTTPS настройте `APP_ORIGIN` и `COOKIE_SECURE=true`, закройте внешний доступ к PostgreSQL. Смена `SESSION_SECRET` отзывает все старые сессии.

В версии 1.0 нет самостоятельного восстановления пароля: ответственный меняет значение в окружении. Не используйте демонстрационную базу для настоящего учёта.
